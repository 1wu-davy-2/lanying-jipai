# 业务流程与状态机设计

## 1. 核心角色与职责

- **商家**：注册认证 → 发布寄拍单（填写样品信息、拍摄要求、佣金金额、寄件地址）→ 达人抢单后寄出样品 → 收到达人寄回的素材/样品后验收 → 验收通过触发佣金结算给达人；验收不通过可申请「争议」，交给平台仲裁。
- **达人**（模特/摄影师）：注册认证（需登记真实姓名、支付宝账号，用于后续提现）→ 浏览「抢单大厅」→ 抢单（乐观锁防止多人抢到同一单）→ 填写收货地址、等待商家寄出 → 确认收货 → 拍摄 → 上传素材 → 寄回样品（填写寄回快递单号）→ 等待商家验收 → 验收通过后佣金进入达人「可提现余额」→ 发起提现申请（填支付宝账号，系统已存默认值可修改）。
- **平台管理员**：审核达人实名资料、监控所有订单、处理超时/争议、处理提现申请（含子职能"交易员"动作：线下转账后登记转账流水号，系统据此把提现单状态改为「已完成」）。

## 2. 订单状态机

订单表 `orders.status` 字段的状态流转如下：

```
DRAFT(草稿，可选)
  │ 商家提交发布
  ▼
PUBLISHED(待抢单) ──────────────┐
  │ 达人抢单成功                  │ 商家撤回/超时未被抢单
  ▼                            ▼
CLAIMED(已被抢单，待商家寄出)   CANCELLED(已取消)
  │ 商家填写寄件单号
  ▼
SHIPPED_TO_MODEL(样品寄出中)
  │ 达人确认收货
  ▼
IN_PROGRESS(拍摄中)
  │ 达人上传素材 + 填写寄回单号
  ▼
RETURNED(素材已提交/样品寄回中，待商家验收)
  │ 商家验收
  ├─ 通过 ──────────────► COMPLETED(已完成，触发结算)
  └─ 不通过 ─────────────► DISPUTED(争议中)
                              │ 平台仲裁
                              ├─ 判达人 ──► COMPLETED
                              └─ 判商家 ──► CANCELLED(不结算，可另定责任赔偿走线下)
```

允许的状态跳转以白名单方式在后端硬编码校验（见 `03-api-design.md` 订单状态机校验节），杜绝跳状态。

### 状态字段清单

| 状态码 | 中文含义 | 谁能触发 | 触发动作 |
|---|---|---|---|
| DRAFT | 草稿 | 商家 | 保存但未发布 |
| PUBLISHED | 待抢单 | 商家 | 提交发布 |
| CLAIMED | 已抢单待寄出 | 达人 | 抢单 |
| SHIPPED_TO_MODEL | 寄件中 | 商家 | 填写寄件快递单号 |
| IN_PROGRESS | 拍摄中 | 达人 | 确认收货 |
| RETURNED | 待验收 | 达人 | 上传素材+填寄回单号 |
| COMPLETED | 已完成 | 商家/管理员 | 验收通过 / 仲裁判达人 |
| DISPUTED | 争议中 | 商家 | 验收不通过并说明原因 |
| CANCELLED | 已取消 | 商家/系统/管理员 | 撤回、超时、仲裁判商家 |

## 3. 抢单并发控制

多个达人可能同时点击「抢单」按钮，需要保证一单只能被一人抢到：

- 方案：数据库层用「条件更新」实现乐观锁 —— `UPDATE orders SET status='CLAIMED', model_id=:mid, claimed_at=NOW() WHERE id=:oid AND status='PUBLISHED'`，判断 `affected_rows == 1` 才算抢单成功，否则返回"该订单已被抢走"。
- 不引入 Redis 分布式锁，MVP 阶段数据库原子更新足够。并发量上来后可加 Redis 抢单队列，标注为后续扩展点。

## 4. 资金流转：结算与提现（人工转账模式）

> 明确不接入微信支付/支付宝支付网关，仅在系统内记账，提现由人工在支付宝 App 内转账后回填流水号确认。

### 4.1 涉及的资金表

- `wallets`：每个达人一条余额记录，含 `available_balance`（可提现余额）、`frozen_balance`（提现审核中冻结的金额）。
- `wallet_transactions`：余额变动流水（订单结算入账、提现扣减、提现驳回退回等），每条都关联订单或提现单，保证可追溯、可对账。
- `withdrawals`：提现申请单，含支付宝账号、金额、状态、交易员登记的转账流水号、备注。

### 4.2 结算流程

1. 订单进入 `COMPLETED` 后，后端在同一数据库事务里：写入 `wallet_transactions`（类型 `ORDER_SETTLEMENT`，金额为订单佣金）+ 更新对应达人 `wallets.available_balance += 佣金`。
2. 佣金金额固定为订单创建时商家填写的 `commission_amount`，MVP 阶段不做平台抽佣扣减（如后续要抽佣，在此步骤加一行 `PLATFORM_FEE` 流水即可，字段已预留 `platform_fee_rate`）。

### 4.3 提现流程

```
达人发起提现申请（填写/确认支付宝账号 + 金额，金额 ≤ available_balance）
   │ 系统：available_balance -= 金额，frozen_balance += 金额，withdrawals 新建 PENDING
   ▼
管理员/交易员在后台「提现审核」列表看到 PENDING 申请
   ├─ 驳回 ──► withdrawals.status = REJECTED，frozen_balance -= 金额，available_balance += 金额（退回）
   └─ 通过 ──► withdrawals.status = APPROVED（表示"可以去转账了"）
                  │ 交易员线下在支付宝完成转账
                  ▼
              交易员在后台「登记转账」：填入支付宝转账流水号/凭证
                  │ 系统：withdrawals.status = COMPLETED，frozen_balance -= 金额（正式核销）
```

- 提现单状态：`PENDING`（待审核）→ `APPROVED`（审核通过待转账）→ `COMPLETED`（转账已登记完成）；或 `PENDING` → `REJECTED`（驳回）。
- 转账流水号字段允许后续手动更正一次（防止交易员登记错误），更正操作记录操作人和操作时间到 `withdrawals.remark`/日志，不允许直接删除记录（资金记录不可硬删除，所有资金表只做软删/追加，不做物理删除）。
- 提现最小金额、单日提现次数限制：MVP 先不做限制，预留 `withdrawal_min_amount` 配置项在 `platform_configs` 表，方便后续调整不用改代码。

### 4.4 对账与安全

- 每次余额变动都必须落一条 `wallet_transactions`，`wallets.available_balance` 定期（或每次读取时）可用 `SUM(wallet_transactions)` 校验一致性，防止并发更新导致余额漂移。
- 更新余额的操作全部包在数据库事务 + `SELECT ... FOR UPDATE` 行锁内，防止同一达人并发提现导致超提。

## 5. 争议处理

- 商家验收不通过时，必须填写不通过原因（文本+可选图片），订单进入 `DISPUTED`。
- 管理员在后台「争议列表」里看双方提交的素材/寄回单号/聊天记录（MVP 阶段暂不做站内即时聊天，双方沟通记录可以是简单的「订单留言板」文本记录），做出仲裁：判达人（订单转 `COMPLETED`，走结算）或判商家（订单转 `CANCELLED`，不结算）。
- 仲裁结果不可撤销，只能由管理员一次性做出（MVP 简化，不做二次申诉）。
